Broken: getPage at detail=properties, and therefore detail=all.

I got a proper diagnosis on that bug this time. It fails on every page, but with a different value quoted each run: "aL" on TEST-PAGE, 1788490063629 on smooth, and a chunk of raw block text on DB Tools. Those are a :block/order string, a millisecond timestamp, and page content respectively. The query is feeding arbitrary property values into a slot that only accepts an entity id or lookup ref. It isn't data-specific — it'll fail on any page holding a non-ref value, which is essentially all of them. Use detail=page and read the property idents off the page entity instead; the values are right there as {"id": N} refs.

getPageUUID is case-sensitive on the title. TEST-PAGE resolves; test-page returns found: false — even though the page's own name field is the lowercase form. Match on title, not name.

Tag entities are pages, so any title shared by a page and a tag will come back ambiguous. That's the guard doing its job — it refuses to pick a write target for you.

Two things worth recording separately.

max_depth doesn't bound the way the name suggests. max_depth=1 still returned the child, while max_nodes=1 correctly dropped it. Depth appears to count levels below the root, so 1 means root plus one generation.

dry_run gave a false positive. createBlock with dry_run: true returned verified: true and "Dry run: Added: {:block 1}." — then the identical real call failed. The dry run validates arguments locally without exercising the write path, so on a build where the route itself is broken it will tell you a write is fine when it isn't. That's a sharper version of the general warning in the skill: dry-run success is not evidence a write will land.
